# vaultchain-upload

Browser-signing upload / download site for the [VaultChain](https://github.com/VaultChainHQ/vaultchain) **devnet**.

> **Devnet only.** Keys are generated in your browser and stored encrypted with your passphrase (the same keystore as the VaultChain web vault). Anyone who gets both the browser profile and your passphrase, or any script running on the site's origin, can take them. The devnet can be reset at any time. Do not use real funds or sensitive data. The UI repeats this warning.

Everything cryptographic happens in the browser: key generation, transaction signing, chunking and Merkle roots, optional encryption, read-token signing and decryption. The node and the storage provider only receive signed transactions, (cipher)text chunks and signed read tokens. There are no server-side secrets.

Related repositories: [vaultchain](https://github.com/VaultChainHQ/vaultchain) (the chain, provider and CLI) · [vaultchain-explorer](https://github.com/VaultChainHQ/vaultchain-explorer) (read-only explorer) · **vaultchain-upload** (this repo). Also: [vaultchain-web](https://github.com/VaultChainHQ/vaultchain-web) (site, docs hub and a profile vault that encrypts keys with a passphrase, unlike the plain-hex storage here).

## What is implemented

| Feature | Status |
| --- | --- |
| Create / import / back up / forget profiles, `vault1…` bech32 address; passphrase-encrypted; legacy plain keys can be migrated | done |
| Guided 7-step upload (profile, funds, files, options, review, upload, done) with cost, retry and a share link + QR | done |
| My files: search, filter, preview, download, share, revoke, deal health; contacts | done |
| Balance (polled from the node) | done |
| Signed transactions (`bank/Send` encoding, `storage/CommitManifest`, `storage/OpenDeal`, `access/GrantAccess`, `access/RevokeAccess`) | done, byte-identical to Go (see tests) |
| Chunking + Merkle content root (port of `pkg/chunk`), per-chunk proofs | done, byte-identical to Go |
| Upload: commit manifest, open deal, upload chunks with `X-Vault-Proof` to the provider, confirm completeness | done |
| Optional client-side encryption (`pkg/vaultcrypt`: XChaCha20-Poly1305 segments, `vle1`, key envelope to your own key) | done |
| Download: signed read token, chunk fetch, Merkle verification against the on-chain manifest, decrypt | done |
| Share: grant read to an address (re-wraps the file key for the grantee), revoke by grant id | done |
| "Shared with me" list and download of files granted to you | done |
| Sending VAULT (`bank/Send`) from the UI | not in the UI (the encoder exists in `lib/vault/msgs.ts`) |
| Hardware wallets | not implemented |
| Files larger than 64 MiB | not supported by this site (the chain allows more; the whole file is held in memory here) |
| Public (`*`) grants on encrypted files | refused on purpose: a public grant cannot carry a key, so it would only expose ciphertext |
| Faucet | the Funds step calls vaultchain-web's `/api/faucet` (100 VAULT, 24 h cooldown per address) |

## Test evidence

`npm test` runs 170+ tests, including a corpus generated by the Go implementation (`tools/tsvectors` in the vaultchain repo, checked in as `test/vectors/go-vectors.json`) and compares byte for byte:

* addresses and RFC6979 signatures for fixed keys, and the full signed tx JSON for 11 transactions covering every message type,
* chunk roots and Merkle proofs for sizes 0 through 700000, including the 262144 / 262145 byte chunk boundaries,
* read tokens,
* vaultcrypt ciphertexts produced by Go decrypt in TypeScript, and TypeScript round trips, tamper / reorder / truncation rejection,
* key envelopes produced by Go open in TypeScript.

`npm run test:live` is an **opt-in** end-to-end test against the real devnet (it spends a little devnet money). Set `VAULT_LIVE_PRIVKEY` to a funded key's 64 hex chars (and optionally `VAULT_LIVE_GRANTEE` to another vault address that has signed a tx before). It uploads a multi-chunk plaintext file and an encrypted file, downloads and verifies both, and grants then revokes access.

## Run locally

Requires Node 20.9+ (CI uses 22).

```bash
npm install
npm run dev        # http://localhost:3000
npm run lint && npm run typecheck && npm test && npm run build
```

`npm run e2e` drives a headless Chrome through the whole flow on a deployed copy with a throwaway profile funded by the faucet (set `BASE`, default `http://localhost:3000`; needs `playwright-core` and Chrome). See [docs/UX-AUDIT.md](docs/UX-AUDIT.md) for what changed and why.

Deep links: `/files?open=<file id>` opens a file; `/files`, `/contacts`, `/account` are the other pages.

## Configuration (Vercel environment variables)

No secrets are required. All variables are optional; the defaults point at the public devnet.

| Variable | Default | Purpose |
| --- | --- | --- |
| `NEXT_PUBLIC_VAULT_REST` | `https://vaultl1-devnet.fly.dev` | Node REST endpoint (called directly from the browser; it sends CORS `*`) |
| `NEXT_PUBLIC_VAULT_PROVIDER` | `https://vaultl1-provider.fly.dev` | Storage provider |
| `NEXT_PUBLIC_VAULT_PROVIDER_MODE` | `proxy` | `proxy` or `direct`, see below |
| `NEXT_PUBLIC_FAUCET_URL` | `https://vaultchain-web.vercel.app/api/faucet` | Faucet endpoint (must allow this site's origin) |
| `VAULT_PROVIDER_URL` | the provider above | Server-side target of the proxy |

### Why a proxy?

The provider only answers CORS for origins in its `ALLOW_ORIGIN` setting, and none is configured, so a browser cannot call it from another origin. By default this site therefore forwards provider calls through its own `/api/provider/*` route (a whitelisted, header-filtered pass-through: only the provider's `status`, `v1/objects/<root>[/status]` and `v1/chunks/<root>/<index>` paths; methods GET/HEAD/PUT). Chunks are at most 256 KiB, so Vercel's request body limit is not a problem. If you set the provider's `ALLOW_ORIGIN` to this site's origin, switch to `NEXT_PUBLIC_VAULT_PROVIDER_MODE=direct` to remove the hop.

## Layout

* `lib/vault/` protocol code: `keys`, `chunk`, `msgs`, `tx`, `readtoken`, `vaultcrypt`, REST/provider `client`, high-level `flows`.
* `lib/proxy.ts`, `app/api/provider/[...path]/route.ts` provider pass-through.
* `lib/` app logic: `keystore`, `session`, `flow` (stepper and queue), `cost`, `faucet`, `library`, `qr`, `errors`, `format`.
* `components/` the UI (`flow/`, `library/`, `account/`). `test/` vector and unit tests.
